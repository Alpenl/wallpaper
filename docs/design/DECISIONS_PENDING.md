## 2. 现在就要定

### D-01 MVP 功能范围（17 章 17.2、MVP 发布门槛）
- **要决定**：是否接受 17 章定义的 MVP 范围和发布门槛。
- **现状**：MVP = F-01（桌面挂载）到 F-10（开机自启），加 F-15（签名安装与更新）、F-16（诊断）；F-11 在 MVP 只导入 video，web 放 v1；Web 壁纸（F-12）、Shader（F-14）、本地库（F-13）都在 v1。门槛：上述 AC 全部通过，PB-idle/video/paused 在 Intel iGPU 笔记本和 M1 上达标，W-T1、W-T3、W-T6、W-T9、M1–M4 都有记录（17 章 17.2、17.3）。
- **可选方案**
  | 方案 | 利 | 弊 |
  |---|---|---|
  | A. 按 17 章原样 | 范围和性能目标一致；原型已覆盖挂载、暂停、恢复 | MVP 没有 Web 壁纸，与 Lively/WE 相比素材类型少 |
  | B. 把 F-12 Web 壁纸提进 MVP | 素材类型更全 | 引入 PB-web、Q-B2/Q-B3/Q-S1 这些未决项，验收面变大（08、10 章） |
  | C. 再砍：去掉 F-11 导入 | 更快 | 失去“迁移 Lively/WE 素材”这个痛点的回应（17 章 17.1） |
- **建议**：A。理由：性能是首要目标，Web 壁纸的性能和审核问题（Q-B2、Q-D3）都还没收敛。
- **不定会卡住**：开发排期和验收口径。
- **何时之前**：开始写产品代码前。

### D-02 签名主体与证书（11 章 11.2、11.3；F-15）
- **要决定**：以哪个法律主体发布、Windows 用哪种签名、macOS 是否注册 Developer ID。
- **依据**：EV 证书 2024 年起不再自动获得 SmartScreen 信誉，和 OV 一样要靠下载量积累，且信誉跟着发布者身份走（11.2）。Artifact Signing 约 $9.99/月、无需硬件令牌、可接 CI，但**组织需在美国、加拿大、欧盟或英国，个人开发者目前只限美国**（11.2）。macOS 直接分发需要 Developer ID 签名 + 公证（11.3）。F-15 的验收要求 SmartScreen 显示发布者名称、Gatekeeper 直接放行（17 章）。
- **可选方案**
  | 方案 | 利 | 弊 |
  |---|---|---|
  | A. Artifact Signing | 便宜、接 CI 方便 | 受主体所在地区限制 |
  | B. OV 证书 | 不受上述地区限制 | 通常需要硬件令牌或云 HSM，CI 集成麻烦（11.2 的对比）；信誉同样要积累 |
  | C. EV 证书 | — | 已不再带来 SmartScreen 优势（11.2），不推荐 |
- **建议**：先确定发布主体及其所在地区：符合条件用 A，否则用 B；同时注册 Apple Developer Program。理由：信誉积累只能靠同一身份持续发布，越早固定身份越好。
- **不定会卡住**：F-15 无法验收；对外测试版会弹 SmartScreen 警告；MyGo 的 mac 签名和公证流程无法配置。
- **何时之前**：首个对外测试版之前，越早越好。

### D-03 商业模式（17 章 17.1）
- **要决定**：产品是否收费、在哪里收费。文档目前只写了“本地功能全部免费，不放广告（商业模式另定）”。
- **它影响的其他决策**：D-06（是否走 Microsoft Store）、D-12（是否做 MAS 版）、D-15（遥测）；律师问题 L-2（专利费按件计，收费与否和出货量相关，见 11.6 的 Via LA 条款）。
- **可选方案**（文档里没有比较过各方案的收入数据，这里只列与技术和分发相关的利弊）
  | 方案 | 与文档相关的利 | 与文档相关的弊 |
  |---|---|---|
  | A. 完全免费 | 符合 17.1 的痛点回应 | 签名、托管等持续成本没有收入覆盖 |
  | B. 本地免费 + 以后的在线画廊或创作工具收费（F-25） | 不违背“本地功能全部免费” | F-25 被列为“以后”，短期没有收入 |
  | C. 商店付费版（MSIX / MAS） | 商店处理支付 | MAS 版功能要裁剪（11.3）；依赖 D-06、D-12 |
- **建议**：现在先拍板一句话原则：是否收费、收在哪里。细节等 MVP 之后再定。理由：这条原则会改变律师问题的前提和商店渠道的取舍。
- **不定会卡住**：L-2 无法问清楚；D-06、D-12 无法定。
- **何时之前**：去问律师之前。

### D-04 mpv 与 Media Foundation 的选择规则（ADR-002、ADR-004、Q-W10、Q-V3）
- **要决定**：W-T3b 结果出来后按什么规则定 Windows 渲染器，以及 10% 容差是否合适。
- **依据**：ADR-002 的 Windows 部分在第 14 轮降为“暂定”。理由是 ADR-003 已统一转码为 H.264，MF 的格式覆盖劣势基本消失，而且改用 MF 可以去掉 GPL 依赖（README 的 ADR 备选方案）。TEST_PLAN W-T3b 的判定规则是：MF 在 CPU、GPU、内存上都不比 mpv 差超过 10%，并且循环点和恢复测试都通过，就改用 MF；否则维持 mpv。10% 是【推断】。原型的已知差异是 MF 从 L3 恢复时从头播放，mpv 能续播（Q-V3）。
- **可选方案**
  | 方案 | 利 | 弊 |
  |---|---|---|
  | A. 维持 10% 规则 | 偏向消除 GPL 依赖（ADR-004、Q-L1） | 10% 没有数据支撑 |
  | B. 严格规则：MF 必须不差于 mpv | 性能优先 | 可能为了很小的差距保留 GPL 依赖和法律风险 |
  | C. 不管性能，直接选 MF | 法律最简单 | 违背“性能首要”；MF 的循环与统计尚未在真机验证（Q-W12） |
- **建议**：A，并补三条，在测试前写进 TEST_PLAN 并签字：
  1. 比较对象是 4K30 片源三次测试的中位数。
  2. 循环点重复帧和 W-T6/W-T9 恢复是硬条件，不计入容差。
  3. Q-V3 的“从头恢复”在 MVP 可以接受，若选 MF 再补续播。

  理由：事先定好规则，结果出来就能直接定案；律师结论（L-1）也可以作为加权项。
- **不定会卡住**：W-T3b 跑完也无法定案，ADR-002/004 和 Q-L1 一直悬着。
- **何时之前**：W-T3b 开跑前。

### D-05 性能预算的地位（17 章 17.3、Q-PB1、README 一页结论第 3 条）
- **要决定**：PB-idle/video/paused 是硬性发布门槛，还是首轮实测后修订一次再冻结。
- **依据**：所有预算都标为【推断，目标】。PB-video ≤ 0.03 核所引用的对照数据“OBS 硬解约 2%”是整机百分比，在 3950X 上折算约 0.6 个逻辑核，所以 0.03 核**没有同类实测支撑**（Q-PB1、17 章脚注）。PB-web 每屏 ≤ 300 MB 低于 box 上的参考值 442–445 MiB（软件 GL）。
- **可选方案**
  | 方案 | 利 | 弊 |
  |---|---|---|
  | A. 现值即硬门槛 | 标准清楚 | 很可能因为目标本身不现实而无法发布 |
  | B. 首轮实测后修订一次，然后冻结为门槛 | 有数据依据，也不会无限放宽 | 需要先跑完交接清单阶段 2 |
  | C. 只作参考，不作门槛 | 灵活 | 与“性能首要”的定位冲突 |
- **建议**：B。PB-paused、PB-idle 现在就可以作为门槛；PB-video 等 W-T3/M3 数据出来后修订一次。理由：PB-video 目前没有依据，而另外两个有 07 章的设计依据。
- **不定会卡住**：MVP 发布门槛无法判定；W-T3b 的比较也缺少绝对参照。
- **何时之前**：交接清单阶段 2 开跑前。

## 3. 真机测试前要定 / 可以慢慢定

### D-06 Windows 是否 MSIX/Store 首发（ADR-006、Q-W7、F-21）
- **要决定**：首发用 NSIS 按用户安装包，还是 MSIX/Store。
- **依据**：Store 安装的应用由微软重新签名，**不会出现 SmartScreen 警告**；但 `windows.startupTask` 要用户先手动启动一次才生效，被用户禁用后应用不能用代码重新启用；AppData 写入会被重定向（11.1）。MSIX 包内能否挂载 WorkerW 还没验证（Q-W7，W-T8）。ADR-006 当前是“NSIS 先行、MSIX 第二阶段”，推翻条件是 W-T8 通过。
- **可选方案**
  | 方案 | 利 | 弊 |
  |---|---|---|
  | A. NSIS 首发（现 ADR） | 没有 MSIX 限制，自启简单 | 要自己积累 SmartScreen 信誉（D-02） |
  | B. Store 首发 | 没有 SmartScreen 警告 | Q-W7 未知；自启受限；与 D-03 有关 |
  | C. 两者同时 | 覆盖面广 | 签名、测试、更新通道都要两套 |
- **建议**：A；规则写成“W-T8 通过，并且 D-03 不排斥 Store，才考虑提前做 Store 版”。
- **依赖的真机测试**：交接清单 5.1（W-T8）。
- **不定会卡住**：安装和更新方案、签名工作量。
- **何时之前**：W-T8 开跑前定好规则。

### D-07 电池策略默认值（07 章 7.4；F-05）
- **要决定**：`batteryPolicy` 的默认值（`pause` / `fps15` / `ignore`），以及低电量阈值 `lowBatteryPct`。
- **依据**：07 章 7.4 的默认值是 `pause` 和 20，标为【推断】起点。F-05 的验收要求“拔掉电源 ≤ 1 s 生效，策略可以在设置里切换”。另外原型的限帧（FPSCap）还没实现（prototype/README）。
- **可选方案**：`pause` 最省电，但用电池时壁纸就不动了；`fps15` 保留动态效果，按解码负载与帧率成正比估算约为 PB-video 的一半（17.3 PB-battery），但限帧尚未实现；`ignore` 的体验与插电时一致，耗电最多。
- **建议**：默认 `pause`、低电量 20%。理由：与性能和省电定位一致；`fps15` 依赖未实现的限帧。
- **不定会卡住**：交接清单 3.2 没有判定标准。
- **何时之前**：交接清单阶段 3 开跑前。

### D-08 Web 壁纸 CPU 看门狗阈值（Q-S1、10 章 10.6、PB-web）
- **要决定**：Web 壁纸的渲染进程持续多高的 CPU、持续多久，才提示用户“占用过高”；是只提示还是强制停止。
- **依据**：10 章 10.6 是“持续 60 s 超过 0.5 核就提示”；PB-web 同样写了这个阈值，宿主自身 ≤ 0.02 核（17.3）；是否合理列为 Q-S1。
- **可选方案**：A. 0.5 核 / 60 s，只提示；B. 更严，例如 0.25 核；C. 超阈值后自动降到 L1。
- **建议**：A。理由：Web 壁纸在 v1，先用温和的规则收集数据；这个阈值也是交接清单 4.3 的判定依据。
- **依赖的真机测试**：交接清单 4.1、4.3。
- **何时之前**：交接清单阶段 4 开跑前。

### D-09 是否投入 DComp visual 方案（Q-W2，03 章 W-T2b）
- **要决定**：是否研发“在 WorkerW 下直接用 DirectComposition visual”，以省掉一次子 HWND 合成。
- **依据**：没有找到开源实现，列为原型项 W-T2b（03 章）。README“当前状态”把它列为决策项：只有 W-T3 显示合成开销明显时才值得。
- **可选方案**：A. 不做；B. 现在就做原型；C. W-T3 数据出来后再按规则决定。
- **建议**：C，规则现在就定：W-T3 中 3D 占用明显超出 PB-video（iGPU 3D ≤ 5%）时才立项。
- **何时之前**：规则现在定，执行与否在 W-T3 结果出来后立即定。

### D-10 每个虚拟桌面一张壁纸（Q-W3）
- **依据**：需要未公开的 IVirtualDesktopManager COM 接口，MVP 不做（03 章）。
- **方案**：做（体验好；未公开接口随系统更新可能失效）/ 不做。
- **建议**：不做，v1 规划时再评估。不定也不会卡住 MVP。

### D-11 macOS 锁屏动态壁纸（Q-M3、F-23）
- **依据**：普通窗口无法显示在锁屏上；现有做法是覆盖系统的 Aerial 文件，macOS 14–15 需要管理员权限（04 章、11.3）；MAS 版不可行（沙盒，2.4.5(v)）。F-23 已列为“以后，只在直接分发版做实验，默认关闭”。
- **建议**：维持 F-23 的定位。不定也不会卡住 MVP。

### D-12 MAS 版是否保留 Web 壁纸（Q-D3）
- **依据**：App Review 2.4.5(iv) 禁止下载“改变应用功能的额外代码”，Web 壁纸里的 JS 是否算在内**尚不明确**。倾向于认为可以接受（属于用户数据，并且运行在 WebKit 沙盒里），但有审核风险（11.3）。ADR-006 已规定 MAS 版里 Web 壁纸默认禁网。
- **方案**：保留并默认禁网（功能一致，但可能被拒）/ 去掉（审核稳妥，但功能少）。
- **建议**：保留并默认禁网，被拒再去掉；前提是 D-03 决定要做 MAS 版。

### D-13 WebM 解复用器（Q-M4，06 章 6.6）
- **依据**：macOS 导入 VP9/WebM 时，解复用用 libavformat（LGPL，动态链接）还是 BSD 实现“还没定”（06 章 6.6）；MAS 版要求单一自包含 bundle（11.3）。
- **方案**：libavformat（成熟，有 LGPL 义务）/ BSD 实现（许可证简单，成熟度待评估）。
- **建议**：先评估 BSD 实现的成熟度和体积，许可证部分问律师（L-3）。WebM 导入不在 MVP，不会卡住 MVP。

### D-14 Linux 发布时间点（F-24、05 章、Q-L7）
- **依据**：05 章明确 Linux“仅作兼容参考，不是 MVP 目标”，因为 GNOME 每个大版本都可能改内部 API，维护成本高；mutter 49 起删掉了扩展依赖的 `hide_from_window_list`（Q-L7）。F-24 列为“以后”。
- **建议**：维持“MVP 之后”。首个 Linux 版只做 KDE 插件和 GNOME 46–48 扩展，GNOME 49+ 适配等有用户需求再做。

### D-15 远程遥测（ADR-010、F-20）
- **依据**：ADR-010 规定默认关闭、只报聚合统计；否决“完全不做”的理由是会失去真机性能分布数据（README ADR 备选方案）。F-20 在 v1。
- **建议**：维持 ADR-010，v1 做；需要的后端服务和隐私文案到时再定。

## 4. 需要问律师的问题（非法律意见）
以下问题都可以直接拿去问律师，背景都摘自 11 章。

**L-1（Q-L1，ADR-004）mpv.exe 随产品分发**
> 我们的闭源（或非 GPL）桌面应用打算把 GPLv2+ 的 mpv.exe（链接 FFmpeg）作为独立程序随安装包分发。主程序只通过命令行参数和 JSON IPC（命名管道）控制它，不链接、不共享内部数据结构。
> 1. 这是否属于 GPL 意义上的“聚合”？依据是 FSF GPL FAQ 的 MereAggregation 条目。
> 2. 我们需要履行哪些义务？我们的理解是：提供 mpv 和 FFmpeg 的对应源码或书面要约、附许可证文本、在 About 页注明，是否足够？
> 3. 如果产品收费（取决于 D-03），结论会变吗？
>
> 补充：如果真机对比后改用 Media Foundation（D-04），这个问题可以撤销。

**L-2（Q-L2）视频专利**
> 产品在用户机器上只调用系统组件解码（Windows Media Foundation 或驱动的 d3d11va，HEVC 由用户自行安装微软 HEVC 扩展；macOS 用 VideoToolbox），导入时的转码也只调用系统编码器，我们不分发任何编解码器实现。
> 1. 对 AVC（Via LA）和 HEVC（Access Advance 等专利池），我们是否负有许可或付费义务？
> 2. HEVC Advance 2016 年条款对“售后下载、完全在通用 CPU 上软件解码的应用”免费；调用 GPU 硬解是否也在这个范围内？
> 3. 若改为分发 FFmpeg 做 WebM 解复用（只解复用，不解码），是否改变结论？

**L-3（Q-M4）LGPL FFmpeg 进入 Mac App Store 版**
> macOS 版可能以动态链接的 dylib 形式使用 LGPL 2.1+ 的 libavformat，按 FFmpeg 官方合规清单构建：不加 --enable-gpl/nonfree、附源码和 configure 参数、About 页注明。MAS 要求单一自包含 bundle 并统一签名，用户难以替换 dylib。
> 1. 在 MAS 渠道分发这样的 dylib，是否满足 LGPL 2.1 允许用户替换库的要求？
> 2. 直接分发版与 MAS 版的结论是否不同？

**L-4（11.4、11.5）开源组件合规清单**
> 请确认这份发版合规清单是否完整：mpv 与 FFmpeg 固定版本随应用发版并对应源码要约（11.7）；所有第三方许可证文本放进 About 页；不使用 libx264 等 GPL 编码库（11.5）。还缺什么？
